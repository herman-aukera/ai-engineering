# EACHAT Final Project Live Proof Runbook

Status: manual external-evidence gate

This runbook exists because deterministic CI must not silently call paid providers or present fixtures as live RAG evidence. The repository-controlled implementation can be green while the final-project submission still lacks real external proof.

## Workflow

Run the GitHub Actions workflow:

```text
Final Project - Live RAG Proof
```

Workflow source:

```text
.github/workflows/final-project-live-rag.yml
```

Select branch `finalproject-GG`. The workflow checks out the exact selected SHA and fails if the checkout differs.

Recommended first run:

```text
provider = openai
effort   = balanced
```

OpenAI is the simplest first proof because the final-project embedding adapter already requires an OpenAI embedding credential. DeepSeek or Kimi can be selected later to prove a different answer provider while keeping the same embedding corpus.

## Required GitHub environment secrets

The workflow uses the existing `eachat-live-smoke` environment. At minimum the first OpenAI run requires:

```text
OPENAI_API_KEY
```

Optional provider selections additionally require their corresponding configured credential:

```text
DEEPSEEK_API_KEY
KIMI_API_KEY or MOONSHOT_API_KEY
```

Do not print, download, paste or commit secret values. The workflow writes only sanitized evidence artifacts.

## What the workflow actually proves

The job creates an ephemeral pinned PostgreSQL 16 service and then executes the following sequence:

```text
exact branch SHA
→ frozen dependency install
→ fetch 16 allowlisted official documentation pages
→ section-aware chunking
→ real OpenAI embeddings
→ PostgreSQL persistence
→ new-process retrieval evaluation
→ bounded live provider answer through the EACHAT graph
→ verify retrieved source refs survive into graph evidence
→ secret scan
→ upload sanitized evidence bundle
```

The new-process retrieval evaluation is intentional: ingestion and evaluation run in separate Python processes against the same PostgreSQL service, so a passing run proves that retrieval is using persisted state rather than an in-process fixture.

## Expected artifacts

A successful workflow uploads one artifact named approximately:

```text
final-project-live-rag-openai-balanced
```

It contains:

```text
final-project-ingestion.json
final-project-retrieval-report.json
final-project-live-answer.json
```

The files deliberately exclude prompts, answer bodies and credentials.

### `final-project-ingestion.json`

Expected minimum facts:

- `sources_ingested == 16`;
- `active_chunks >= 16`;
- 16 entries in `chunks_by_source`;
- `embedding_model == text-embedding-3-small`.

### `final-project-retrieval-report.json`

Generated by:

```text
evals/energy_chat/final_project_eval.py
```

The workflow is RED if a retrieval case with an expected internal source misses all expected source ids at `k=5`. The report is retrieval evidence only; it does not pretend to measure disposition accuracy.

### `final-project-live-answer.json`

Generated by:

```text
scripts/smoke_eachat_final_project_live.py
```

It records safe operational facts such as retrieval strategy, retained evidence count, source ids, served provider/model, provider-call count, latency/cost when available and final disposition. It records neither the user prompt nor the answer body.

The proof requires exactly one answer-provider call and forbids provider fallback for this smoke path.

## Failure handling

Do not convert a failed live workflow into a documentation claim.

If source acquisition fails, retain the source and HTTP failure. If retrieval misses an expected source, inspect chunking/query relevance and rerun after a reviewed change. If a credential is missing, configure it in the GitHub environment rather than inserting it into YAML. If the provider call fails, retain that failure as live-provider evidence and keep deterministic CI independent.

## Submission evidence

After a successful run, retain the workflow run URL and artifact name in the final submission evidence. The artifact proves the live RAG/provider slice for that exact SHA only.

The assignment still requires an accessible demonstration path: a public deployment URL **or** the required 2–3 minute video. The live-proof workflow does not satisfy that separate requirement by itself.
